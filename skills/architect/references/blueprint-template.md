# 架構建議書模板：`solution/03-blueprint.md`

每一節都要填。寫給使用者本人看：業務語言為主，技術名詞出現時附一行白話解釋（講法照 [glossary.md](glossary.md)，全文同一個詞用同一種講法）。每一句都要是唸得順的完整句子，不寫電報體。價格若未即時查證，統一註記「撰寫時參考價，請以官網為準」。

```markdown
# 架構建議書：〈專案名〉

> 幫〔誰〕把〔什麼事〕從〔現況〕變成〔更好〕。
> 本建議書依 2026-XX-XX 的需求摘要與資源盤點撰寫；價格為撰寫時參考價。

## 一、結論（三句話）

1. **形態**：Web／PWA／APP——一行理由。
2. **怎麼做**：〔前端〕＋〔後端/資料庫〕＋〔部署〕，一句話。
3. **花多少**：起步每月 $X（一次性 $Y）；到〔什麼規模〕前不會漲。

## 二、要不要寫程式？

第 0 關的判定與理由。若判定「先用現成服務」，後面各節改寫成：用哪個服務、
怎麼設定、什麼訊號出現（費用、限制、資料掌控）再回來走自建，並保留成本比較表。

## 三、Web / PWA / APP 判定

把需求證據對照表列出來（哪幾條指向哪個結論）。若結論是 APP，加寫：
跨平台方案選哪個與理由、隱形成本（開發者帳號年費、審查、更新上架）、
哪些部分留在 Web 不進 APP。

## 四、技術選型

| 層 | 選什麼 | 為什麼是它 | 什麼情況該換掉 |
|----|--------|-----------|----------------|
| 前端 | | | |
| 後端 | | | |
| 資料庫 | | | |
| 部署 | | | |
| （其他） | | | |

每列的「為什麼」必須引用需求或資源的事實（「因為你熟 Vue」「因為只有表單 CRUD」），
不可以只寫「業界主流」。

## 四之一、外觀方向

寫出階段 1 選定的風格（俐落／雜誌／溫暖＋使用者的形容詞），並從 style-presets.md
抄入該風格的**完整規格**（字體、色彩、形狀、元件庫）與**通用反 AI 味清單**。
結尾提醒一句：「開工時，把這一節整段連同需求交給實作的 AI，並明說避免通用模板臉。」

## 五、服務清單與費用

一眼看懂的「服務 = 角色（費用）」表：

| 服務 | 角色 | 起步費用 | 之後什麼時候要付、付多少 |
|------|------|----------|--------------------------|
| 例：Cloudflare Pages | 部署 | 免費 | 幾乎不會需要付 |
| 例：Supabase | 資料庫＋登入 | 免費 | 資料庫超過 500MB 或要天天備份 → $25/月 |

## 六、每月成本總表

| 項目 | 起步期 | 成長期（〔定義成長訊號〕後） |
|------|--------|------------------------------|
| 服務費小計 | $X/月 | $X'/月 |
| 一次性（網域、開發者帳號…） | $Y | — |
| **你的時間** | 開發約 N 小時 | 維運約 M 小時/月 |

## 七、刻意不做清單

| 現在不做 | 為什麼 | 什麼訊號出現才做 |
|----------|--------|------------------|
| 例：原生 APP | Web 推播已夠用 | 使用者明確要求商店安裝、或需要背景定位 |
| 例：自動擴展/K8s | 免費層可撐一萬人 | 尖峰流量讓頁面變慢且付費層也不夠 |

## 七之一、開工資源與預裝包（我們是目錄，不重造輪子）

對照第四節的每個選型，列出「不用自己做」的成熟資源：官方 SDK、skill、MCP、
官方文件。來源見 skill-index.md，只列跟這個專案有關的，每項一行：
資源名稱｜它幫你省掉什麼｜連結。
另按 skill-index.md 的「預裝包」挑出這個專案適用的包（基本包人人都有；
收個資或金流必加安全包），並在交付時主動提議：「要不要我現在就裝好？」

## 八、上線路線圖

- **第一週**：〔最小可用範圍〕——砍到只剩驗證成功指標所需的功能
- **第一個月**：〔補上的東西〕
- **檢查點**：三個月成功指標（沿用需求摘要 Q8）；達標下一步／未達標怎麼收
- 使用者是用 Claude Code 開發的話，附一句：拿這份建議書 + `solution/01-requirements.md`
  直接請 Claude 開工即可。

## 九、風險與逃生路線

- **金鑰管理（必寫）**：金鑰只放 `.env`（確認在 `.gitignore`）或平台 secret，
  絕不進程式碼；外洩處置＝立刻作廢重發。
- 每個關鍵服務一行：倒了／漲價了往哪搬、資料怎麼帶走（例：Supabase 是標準
  Postgres，`pg_dump` 即可全量搬走）。
- **退場條款（必寫）**：「連續 N 個月活躍低於 X，或年維護成本超過 Y，
  則 90 天內啟動退場」——數字由使用者的成功指標推導。

## 十、上線檢查清單（10 項全勾才叫可以上線）

照 skill-index.md「上線與維護」的 10 項清單原文列出，每項可核對；
另附維護節奏（週 15 分／月 1 小時／季半天）。涉及個資或金流時，
加一行「隱私權政策與法遵請洽專業人士」。
- 法遵留白：需求有敏感資料或發票義務時，明列「請洽會計師／法務確認」的項目。
```

## 寫作紅線（覆述，違反就重寫）

- 每個數字可驗證：費用有來源、額度有數字，不寫「很便宜」。
- 「為什麼是它」不能是空話：必須連回這位使用者的需求或資源。
- 建議書不該出現使用者養不動的零件（對照階段 2 的維運底線）。
- 全文使用者看得懂：每個技術名詞第一次出現時，括號一行白話。
