# 階段 3 判斷流程：從需求＋資源到架構

照關卡順序走。每一關的結論都要能在建議書裡用一行說出「為什麼」。

## 第 0 關：需不需要寫程式？

**誠實是這個 skill 的招牌。** 下列情況，正確答案是現成服務，不是開發：

| 需求長這樣 | 先建議 | 什麼時候才值得自建 |
|------------|--------|--------------------|
| 表單收資料、報名 | Google 表單 / Tally | 要複雜邏輯、要接自家資料庫 |
| 一頁式官網/活動頁、幾乎不改 | Canva 網站 / Google Sites，或靜態頁 | 要自訂互動、要掛自己的網域與分析（靜態頁本來就便宜，門檻很低） |
| 個人接案/課程預約 | Calendly / SimplyBook | 要跟自家會員、金流深度整合 |
| 小量電商（幾十個品項） | 蝦皮/現成開店平台（SHOPLINE、EasyStore） | 抽成與月費超過自建成本，或要完全掌控體驗與資料 |
| 團隊內部追蹤表 | Notion / Airtable / Google 試算表 | 多人同時改造成資料亂掉、要權限控管、要自動化 |
| 知識庫/文件站 | Notion 公開頁 / GitHub Pages | 要全文搜尋、多語、自訂樣式 |

判斷原則：**每週省下的時間 × 三個月 < 開發時間**，就用現成的。反過來（現成服務的月費、抽成或限制三個月內就會讓人後悔），才進第 1 關。

「先用現成的」不是拒絕開發，建議書可以規劃「第一個月用現成服務驗證，訊號 X 出現再自建」的兩階段路線。

## 第 1 關：Web、PWA、還是 APP？

**預設答案是 Web。** 只有證據（階段 1 的 Q4）指向必要，才往右走。逐條核對：

| 需求證據 | Web | PWA（加到主畫面） | 原生/跨平台 APP |
|----------|-----|-------------------|-----------------|
| 手機為主、要有「APP 的感覺」 | ○ | ✅ 夠用 | 不必要 |
| 推播通知 | ✗ | ✅ iOS/Android 都已支援 Web Push（iOS 需先加入主畫面；到達率與穩定度仍略遜原生） | ✅ 最穩 |
| 相機拍照上傳、掃 QR code | ✅ 都做得到 | ✅ | 不必要 |
| 取得目前位置 | ✅ | ✅ | 不必要 |
| **背景**持續定位（跑步軌跡、外送追蹤） | ✗ | ✗ | ✅ 只有 APP 行 |
| 藍牙 BLE / NFC 讀寫 | Android Chrome 部分可、iOS 幾乎不行 | 同左 | ✅ 要穩就 APP |
| 離線唯讀（看過的內容再看） | ○ | ✅ Service Worker 夠用 | 不必要 |
| 離線操作再同步 | 難 | △ 可做但費工 | ✅ 較穩 |
| 桌面 Widget、手錶、健康資料（HealthKit 等） | ✗ | ✗ | ✅ 只有 APP 行 |
| 「一定要上架商店」（老闆指定/族群習慣） | ✗ | ✗ | ✅ 直接成立 |

判定規則：

1. **任何一條落在「只有 APP 行」→ APP**；否則
2. **手機為主 或 需要推播 → PWA**（本質還是 Web，加離線快取與推播，成本只多一點）；否則
3. **Web**。

要做 APP 時的附帶決策：

- 一律先考慮**跨平台**：已是 Web 技術棧 → Capacitor 包殼＋原生插件；要接近原生體驗 → Expo (React Native)；團隊熟 Dart 或要高度客製 UI → Flutter。**單平台原生（Swift/Kotlin）只在深度硬體整合或效能極限時選。**
- 提醒隱形成本：Apple Developer US$99/年、Google Play 一次性 US$25、審查天數、每次更新要重新上架。**能 Web 的部分留在 Web（帳號管理、後台、行銷頁都不要塞進 APP）。**
- App Store 不收「純網頁包殼」的 APP（審查指南 4.2 最低功能門檻）——包殼上架至少要加推播、原生分享、離線等原生能力才過得了。
- 桌面軟體同理：預設 Web；真的要桌面版，Tauri 優先於 Electron（體積與記憶體小一個數量級），除非需要 Electron 生態的特定套件。

## 第 2 關：技術選型

### 選型總原則（寫進建議書的理由都從這裡來）

1. **熟的贏過潮的**：使用者或幫手已熟的技術，直接加 3 分。
2. **AI 助手寫得好的贏過小眾的**：主流 = 訓練資料多 = AI 出錯少。React/Vue、Node/Python 這一級才算主流。
3. **零件越少越好**：每多一個服務就多一個會壞的東西。先問「這個零件不裝會怎樣」。
4. **可逆的決定快快做**：換 UI 框架、換部署平台是可逆的，不要糾結；資料庫和金流是難逆的，多想一步。

### 前端

| 情況 | 建議 | 一行理由 |
|------|------|----------|
| 內容展示、極少互動 | 靜態網站產生器（Astro）或甚至純 HTML | 沒有伺服器就沒有維運；快、便宜、不會壞 |
| 一般 Web 應用（表單、清單、儀表板） | **Next.js（React）或 Nuxt（Vue）擇一** | 主流全端框架：路由、SSR、API 一次到位；React 生態最大、Vue 上手較平緩，熟哪個用哪個，都不熟選 React（AI 與範例最多） |
| 重 SEO 的內容＋部分互動 | Astro + 少量互動島 | 內容站的效能天花板高 |
| 內部工具、不在乎 SEO | 同上主流框架即可（純 SPA 也行） | 內部工具別花時間搞 SSR |

CSS 一律建議 Tailwind CSS（AI 產出品質穩定、不用命名煩惱）。元件庫**跟著階段 1 選的外觀方向走**（見 [style-presets.md](style-presets.md)）：俐落 → shadcn/ui（React）或 shadcn-vue；雜誌 → Tailwind 自組；溫暖 → DaisyUI 或 Tailwind 自組。

### 後端

| 情況 | 建議 | 一行理由 |
|------|------|----------|
| 只有表單/清單 CRUD＋登入 | **BaaS（首選 Supabase）**，不自建後端 | 資料庫、登入、權限、檔案一次給齊，免費層夠小專案用很久 |
| 有自訂商業邏輯（計價、排程、串接第三方） | 全端框架的 API 層（Next.js API routes / Nuxt server routes）＋ BaaS 當資料庫 | 邏輯放框架裡，還是不用自己管伺服器 |
| 重運算、AI 推論、長任務 | 上面之外加一個 Python 服務（FastAPI）託管在 Railway/Render/Fly.io | Python 生態在 AI/資料處理無可取代；只把重的部分拆出去 |
| 公司政策要求資料落地/自管 | VPS（Hetzner/Linode）+ Docker Compose | 唯一建議自管的理由是「被要求」；成本表要加每月維運時數 |

**反模式警告**：< 1 萬人用的產品出現微服務、Kubernetes、自建 CI/CD 集群、多區部署——全部打回。單體 + 託管平台可以撐到你根本到不了的規模。

### 資料庫

- **預設 PostgreSQL**（透過 Supabase 或 Neon 託管）。關聯資料、JSON、全文搜尋、向量（pgvector）一顆全包——「要不要另外加向量資料庫/搜尋引擎」的答案幾乎都是「先用 Postgres 內建的」。
- 純快取/計數才考慮加 Redis（Upstash 免費層）；資料量真的大到 Postgres 撐不住再說（那是好幾年後的事）。
- 檔案（圖片、附件）放物件儲存：Supabase Storage 或 Cloudflare R2（流量免費是 R2 的殺手鐧）。

### 部署

| 東西 | 放哪 | 理由 |
|------|------|------|
| 靜態站 | Cloudflare Pages 或 GitHub Pages | 免費、全球 CDN、Cloudflare 頻寬不限量 |
| Next.js/Nuxt 全端 | Vercel（Next 首選）或 Cloudflare | git push 就部署。注意 Vercel Hobby 限個人非商業，商用要 US$20/月——商用免費就選 Cloudflare |
| Python/長駐服務 | Railway（US$5/月）或 Render（US$7/月） | 免 DevOps 的容器託管。免費層別指望：Railway Free 每月僅 US$1 額度、Render 免費層會休眠、Fly.io 已無免費層 |
| 網域 | Cloudflare Registrar（成本價）或 Namecheap；台灣 .tw 選本土註冊商（行情 NT$550–800/年） | 網域是少數必花的錢：.com 一年約 US$10–15；比價一律看**續約價**，細節見 stack-catalog |

### 台灣在地件（需求有金流/通知/發票才裝）

細節與費率見 [stack-catalog.md](stack-catalog.md) 的台灣區段。重點判斷：

- **收台灣消費者的錢**：Stripe 在台灣仍未開放本地商家收款 → 用綠界 ECPay / 藍新 NewebPay（個人也能申請）或 TapPay（量大再談）。**收海外的錢**才用 Stripe（需要海外公司主體）或 Paddle / Lemon Squeezy（MoR 模式，個人可用）。
- **通知**：台灣使用者黏在 LINE 上——「要推播」的很多情境，正確答案是 **LINE 官方帳號 + Messaging API**，不是做 APP。這常常直接改變第 1 關的判定，要回頭檢查。
- **電子發票**：收款方是公司行號（或個人賣家達到營業稅門檻）就有開發票義務 → 綠界/ezPay 的發票加值服務。個人小額則先確認免辦門檻。這節不確定的部分明寫「請洽會計師確認」。

## 出口檢查（寫建議書前最後一遍）

1. 每月成本加總 ≤ 階段 2 的月預算？超了就降級（付費件換免費件、砍範圍），不是叫使用者加預算。
2. 技術棧的每個零件，使用者（或他的 AI 助手）養得動嗎？
3. 有沒有哪個零件拿掉其實沒差？拿掉。
4. 三個月成功指標（階段 1 的 Q8）用這個架構驗證得了嗎？路線圖第一個檢查點就放它。
5. 金鑰動線清楚嗎？每一把金鑰都該有去處（`.env` 或平台 secret），建議書不該出現任何「把 key 貼進程式」的步驟。
